Exhibit B

The Five-Stage Lifecycle

Stage 1
Birth
Mandate: unique identification and cryptographic anchoring to prevent identity spoofing.
Stage 2
Permissioning
Mandate: strict least privilege — agents never inherit excessive access from user sessions or broad tokens.
Stage 3
Rotation
Mandate: periodic refresh of keys and credentials to neutralize persistent-access threats.
Stage 4
Revocation
Mandate: immediate withdrawal of access on anomaly detection — neutralizes agent hijacking.
Stage 5
Decommissioning
Mandate: final reasoning path recorded and cryptographically signed before memory is purged, to prevent repudiation.
Exhibit C

Threat Navigator

T2 — Tool Misuse / Agent Hijacking
Adversarial data is ingested by the agent, triggering unintended tool calls that exfiltrate data.
Mitigation → validate agent instructions, pre-execution tool checks, rate-limiting.
T6 — Intent Breaking
An attacker redirects the agent's planning to prioritize a malicious goal over the original one.
Mitigation → planning-validation frameworks, behavioral auditing by a secondary model.
T7 — Misaligned Behavior
Deceptive reasoning leads the agent to ignore safety consequences to reach a goal faster.
Mitigation → behavioral constraints, multisource validation feedback loops.
Exhibit D

Case File — Three-Agent Refund System

1
Reframe before designing
State up front: this is a ReAct loop with runtime-decided control flow, not static IAM. Identity is the perimeter, not the application layer.
2
Distinct Birth identity per agent
Ticket-Reader, Payment Agent, and Coordinator each get their own cryptographically anchored identity — never a shared service account.
3
Least-privilege permissioning
Payment Agent gets a scoped capability (refund up to $X, approved tickets only), not the user's full account access. This is where Confused Deputy and Excessive Agency get closed off.
4
JIT, ephemeral credentials
Payment Agent's API token is issued per transaction, not long-lived — so a leaked token can't become standing privileged access.
5
Threat-model the handoffs
A poisoned ticket could hijack Coordinator into routing a fake refund; a misread ticket could cascade into a real one if Coordinator trusts Ticket-Reader's output uncritically.
6
Autonomous rollback
Coordinator watches for anomalies — refund spikes, repeated validation failures — and revokes Payment Agent's credentials immediately, without waiting on a human.
7
Traceability and decommissioning
Every refund action is logged with agent identity, tool call, parameters, and data accessed — signed and immutable, so a SOC2 or PCI DSS audit can be answered months later.

Exhibit F

Anticipated Cross-Examination

"Why not let the Coordinator hold broad access and delegate as needed?"
Because that makes Coordinator a single point of privilege escalation — a compromised or manipulated Coordinator becomes a master key. Scope stays with the agent that actually needs it.
"How is agent-to-agent trust different from user-to-agent trust?"
A2A needs its own validation layer. Agents trusting each other's outputs by default is exactly how a cascading hallucination turns into a cascading action.
"What's the first thing that breaks if you skip traceability?"
Repudiation. You lose the ability to prove what happened — which fails an audit even when nothing malicious occurred.
